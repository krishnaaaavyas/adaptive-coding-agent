## 1. Evaluation population design

An independent authorized construction/certification team must create the future
population from a fixed repository lineage and authenticated public episode/task
ledger. Freeze the construction contract before model discovery and the actual
population manifest before outcomes. The team may later access protected material
under separate authorization; this task and candidate discovery workers may not.

An eligible future target has an authenticated first-availability/release event,
public P, authoritative repository snapshot R_t, private target tests, regression
suite and convention requirements. Record source identities and exact hashes.
History cutoffs precede the target's first availability to any history constructor,
labeler, training process or evaluation-generation process. A target already known
to a history curator cannot be made unseen merely by giving it a later public
release timestamp. Audit constructor access, not only ledger timestamps.

The target must require an authentic repository/team-specific decision grounded
in earlier authorized development history: applicability, boundaries, failure
handling, interfaces, data contracts or other accepted repository behavior. A
generic programming puzzle with no history-dependent repository fact is not a
primary accumulated-experience target. This is a source/semantic judgment before
outputs, not a requirement that a model fail without history.

Produce K_t with the unchanged deterministic draft3 selector from the actual
authorized current snapshot. Do not delete informative documentation/code/tests,
alter anchors, conceal naturally present rules, or select a snapshot to make
history necessary. Use the same P/R_t/K_t and output/generation controls across
all compared conditions/stages; histories vary only through their prescribed route.
Retain K/H overlap and its provenance, as draft3 requires.

Before outcomes, independent semantic certification records a task's class:

| Class | Pre-outcome rule | Permitted interpretation |
| --- | --- | --- |
| HISTORY_INFORMATIVE | A concrete required repository-specific fact is evidenced in eligible history, is not sufficiently specified by public P plus naturally produced K_t, and the history's scope/lineage transfers to this distinct future task. Record the relevant source spans and the missing-context rationale privately. | Eligible primary stratum for an accumulated-experience contrast; classification alone does not prove improvement or necessity. |
| CONTEXT_SUFFICIENT | Public P plus natural K_t already sufficiently supplies the relevant behavior, even if history redundantly supports it. | Retain as control/diagnostic stratum; never count it as evidence that history was necessary. |
| UNCLEAR | Source sufficiency, transfer, independence, scope or curator agreement remains unresolved. | Retain in the audit inventory; no primary claim unless independently resolved and certified before outcomes. |

If reasonable generic coding knowledge plus P/K resolves the decision, do not
certify HISTORY_INFORMATIVE. Classification is external governance; the existing
harness does not automatically prove semantic sufficiency. Record certifier,
cutoff, class, source-span hashes and rationale; do not show these classifications,
private rationales or target expectations to generation/training. No class changes
based on model success/failure. Later discovered defects follow the existing
outcome-independent quarantine/version/rerun policy, not selective exclusion.

Conceptual diversity must cover distinct convention/behavior scopes and transfer
demands where the repository genuinely supports them: application of a prior
boundary to a new path, correction of an analogous interface/behavior in a distinct
component, and interaction with existing regression obligations. Record task-family,
episode/convention ancestry, affected component and dependency graph. Do not force
unsupported families or declare a numerical sample size here. A missing family
limits claim breadth explicitly.

Group paraphrases, shared target solutions, repeated edits of the same defect and
close derivatives of a source episode into common dependency clusters. A future
target that reproduces a training label or merely changes names is not independent
transfer evidence. Keep its disposition/lineage; exclude it from primary unseen
transfer claims before outcomes. Later analysis reports cluster-level dependence
and family coverage rather than treating each variant as an independent replicate.
The inferential/statistical analysis plan and power/sample-size justification
remain a later pre-experiment prerequisite; this conceptual rule does not supply them.

The primary stratum is a common fixed HISTORY_INFORMATIVE population whose relevant
history fact is present at the largest eligible stage; fact availability at each
earlier stage is annotated privately before outcomes. Retain the same targets
across stages so new history is not confounded with easier tasks. Apply all-condition
capacity admission before outcomes; no candidate-specific clipping, target removal
or smaller population to claim support for the full selection envelope.

## 2. Exact training example and source-to-example contract

One eligible example is **one closed, authenticated historical development episode's
active authorized accepted resolution**, represented as its original public
request and pre-attempt deterministic repository context, supervised by complete
replacement contents for the request's canonical targets. It is supervised
accepted-code reconstruction, not reinforcement learning, preference-pair training,
rule induction or training on every token of an interaction transcript.

The accepted resolution must answer that request as issued. A materially changed
request is a distinct episode with its own earlier snapshot and lineage, not a
silent rewrite of the original input. A final patch/diff is usable only after
deterministic authorized application to the exact pre-attempt snapshot and extraction
of full canonical target contents; patch application/version hashes are provenance.
No model infers missing target code or labels. Missing authoritative bytes blocks
example construction, rather than inviting synthetic repairs.

| Field role | Exact contents and treatment |
| --- | --- |
| Provenance-only | Episode/repository IDs, chronology/access/availability events, source/snapshot/body hashes/spans, initial attempt and rejected revisions, accept/reject/edit decision, feedback source, public verification receipt, scope/consent, correction/revision/withdrawal lineage, eligibility reasons and constructor/certifier signatures. No private test answers are copied into feedback records. |
| Model-visible input | Inherited system instruction plus canonical historical public P and exact K from the immutable **pre-attempt** snapshot, serialized as draft3 A with no H intervention. Do not use final implementation in K unless it legitimately predates this episode, in which case overlap is recorded. No private certification wrapper is visible. |
| Supervised target | Exact normalized authorized accepted/corrected full replacement contents, in draft3 canonical target order and complete-replacement grammar. It is this historical episode's approved public implementation, never a current/future evaluation solution. |
| Loss-bearing tokens | Accepted assistant completion's content and required multi-file headers, plus the verified native terminal for that completion. System/user/template framing, padding, previous attempts, feedback, provenance and certification tags carry no loss. Later exact token-boundary/mask verification must prove this without a silent fallback. |
| Prohibited model-visible training fields | Private tests/scorer code/hidden answers, future/current evaluation requests or solutions, benchmark/classification/selection judgments, personal or transient correction text, curated M/C rule/evidence interventions, adaptation outcomes, failed/invalid generated artifacts and unapproved attempt text. |

An input may naturally include ordinary public code/tests/documentation selected
into K. Preserve those bytes even when they contain repository guidance. The
prohibition concerns inserting an extra curated rule/evidence treatment into the
training input; it is not permission to strip natural repository evidence.

The proposed candidate-independent content envelope is inherited historical
P/K input ceilings and complete targets constrained to the existing acquisition
source-file eligibility ceiling. Every target's approved raw source body must meet
draft3 `/budgets/source_raw` before normalization, including newly created targets.
This adoption keeps supervision within the project's existing ordinary-source
regime; it is not a newly guessed training-token length. A target that fails this
criterion is logged as outside this proposed workload regime, never truncated.
The rule is fixed before candidates and cannot be changed to make one fit.

For target vector T, the full completion byte bound is deterministically
`sum(source_raw_limit for each target in T) + exact_multi_file_header_bytes(T) +
required_inter_section_LF_bytes`, with no multi-file framing for a single target.
T is bounded by the inherited canonical public-P byte ceiling, so the envelope is
finite without inventing a target count. Existing normalization does not increase
raw source length. The full training sequence includes inherited system/public
framing, full input, full label and later pinned template/terminal overhead; its
token length is **not** the H prompt budget or evaluation generation reserve.
The historical approved label is already supplied training data, not a generated
evaluation output; adopting the source-file ceiling does not enlarge the future
evaluation output allowance. Later every complete eligible example must fit native
training without shortening; maximum tokens are measured/proven separately.

No splitting, chunking or multi-example sequence packing is authorized by this
proposal. An overlength eligible example blocks candidate/runtime capability or
requires explicit candidate-independent dataset/envelope review. It cannot be
dropped from that candidate's full stage history. Source-ineligible episodes are
distinct from an eligible example that a candidate cannot fit.

### Episode and feedback dispositions

| Episode/feedback class | Supervision and eligibility |
| --- | --- |
| ACCEPTED | Target the approved historical implementation only after repository/team authorization, public verification and source/chronology certification; acceptance alone does not waive provenance/integrity. |
| REJECTED | Unapproved attempts are provenance only, never positive targets or automatic negative examples. If an authoritative later accepted correction resolves the same request, one corrected example becomes available only after that correction's closing/certification events. Otherwise no training example. |
| DEVELOPER-EDITED | Use the authorized final developer-approved implementation as the target; original attempt and edit/feedback sequence stay provenance. The label's availability cannot be backdated to the initial attempt. |
| FAILED/INVALID run | Never train from its raw generated artifact as valid supervision. Quarantine infrastructure/leakage/evaluator-defect episodes. A separately authorized, verified developer-authored repair may produce a new eligible resolution with fresh lineage/certification; no automatic salvage or outcome-based exception. A valid negative test outcome is not automatically an infrastructure defect. |
| TRANSIENT correction | Do not train the shared adapter or assert a persistent convention. Retain bounded-scope authorized feedback privately in provenance; no persistent B/C treatment in this workload. |
| PERSONAL correction | Exclude from shared repository training, shared B/M/C records and shared rules. Explicit private-personal scope/consent does not silently authorize a team adapter; personal adaptation would require a separate protocol. |
| REPOSITORY/TEAM correction | Eligible only with authorized repository/team confirmation of applicability and scope, correction lineage and verification. Code supervision uses its approved resolution, not an invented generalized rule. |

Only non-transient repository/team-authorized implementations enter shared
supervision. Scope is certified before a stage is built, not inferred from the
number of repetitions or whether a model appears to benefit. Mixed-scope episodes
require separable authorized repository-only labels/sources; otherwise exclude
the episode with a recorded reason, not a model-authored redaction.

B episodic memory may expose certified source-faithful historical requests,
attempts and descriptive corrections where authorized, but must not insert an
explicit generalized lesson/rule. A developer's normative repository rule belongs
in confirmed C (and the C lane of BC); B may describe historically attributed
feedback without turning it into a command for the current target. M is descriptive
information matched to C, independently certified. Training target code expresses
accepted behavior; it does not make B/C/weights interchangeable information doses.

## 3. H0/H1/H2/H3 history dataset design

H0 has no eligible accumulated history and no trained adapter. H1/H2/H3 use the
complete active eligible example sets at their chosen pre-target cutoffs. Each
weight stage rebuilds from ORIGINAL with a fresh adapter/optimizer/scheduler/RNG;
no adapter-on-adapter or merged-derivative parent. Non-weight stages use the same
eligible source-prefix view through their own certified B/M/C/BC representation
and unchanged H packing, not the full corpus squeezed into an inference window.

Order uses an authenticated append-only event sequence, with UTC timestamps and
source/access hashes retained. Availability is the last required request/context,
approved resolution, verification, scope authorization, construction/certification
and registry-release event, all actually preceding that cutoff. No backdating,
retroactive certification or using later corrections in earlier stage data.
Stage scopes refer to the same repository/team lineage, with exact source snapshots;
no personal/team cross-contamination or silent cross-repository pooling.

At each cutoff resolve explicit revisions and withdrawals, then exact semantic
example duplicates: identical normalized model-visible input and approved target
bytes with the same scope retain the earliest authenticated availability, then
source-hash/UTF-8 opaque-key order. Keep duplicate provenance and dependency cluster.
No semantic near-duplicate removal is inferred by a model; shared lineage is a
dependence annotation. Invalid chains/conflicting active resolutions block the
stage. Later revisions do not overwrite earlier manifests. Prompt H continues
using its existing draft3 revision/dedup/order rules; this training-example rule
does not replace the H packer.

### Deterministic milestone algorithm, instantiated later

Use only independently authenticated repository release/handoff milestones whose
type, scope and completion policy are defined before corpus construction. A
milestone closes a development interval by an authorized repository/team release
or handoff event; it is not minted to obtain a desired sample size. No milestone
or cutoff is selected from candidate support, training loss or future performance.

For a fixed evaluation cohort, define T as the earliest first-availability event
of its future targets to any constructor/evaluation actor. The cohort and T come
from the candidate-independent population manifest. Consider only completed
milestones strictly before T. Build each milestone's entire certified active
eligible set D(m), using that milestone's own information availability.

1. H3 uses the latest such milestone. Do not move H3 backward to hide a withdrawal,
   contamination or inconvenient resource burden.
2. H2 uses the latest earlier milestone whose entire D(m) is a nonempty proper
   subset of H3's exact active example identities/bytes and which admits an earlier
   nonempty proper-subset milestone for H1.
3. H1 uses the latest earlier milestone whose entire D(m) is a nonempty proper
   subset of H2's exact set. Ties in milestone sequence are invalid ledger state,
   not a cue for a quality-based tiebreak.

Thus H1 is a proper subset of H2, and H2 of H3 when supported by the corpus.
No equal thirds, invented counts, arbitrary spaced dates or history subsampling
is introduced. Differences include complete eligible episodes, not selected
easy examples. The algorithm chooses only intact milestone views and never
removes a superseded record from an earlier view to manufacture nesting.

If the latest pre-target history has no such strict nested milestone chain,
record **LEARNING_CURVE_MANIFEST_BLOCKED** for that cohort. Do not rename identical
datasets H1/H2/H3 or claim a three-stage learning curve. Additional authentic
history/milestones or an independently reviewed revised design is required.
Corrections can make active histories nonnested; this limitation is reported
honestly rather than erasing correction lineage. Metadata instantiation and
eligibility construction occur later without candidate/model outcomes.

Each stage manifest records workload/protocol versions; repository/snapshot IDs;
cohort/first-release/cutoff/milestone bindings; ledger/registry roots; full ordered
active examples and hashes; eligibility/source/scope/correction/duplicate/withdrawal
receipts; full content sizes/counts; contamination/dependence checks; relative
fact availability; and stage coverage. Later append pinned tokenizer/renderer,
complete sequence/loss-mask/token-total receipts and recipe/runtime identities.
Counts/token totals are facts of construction, not proposed requirements here.
Full manifests are required before final candidate resource comparison, as Common
Requirements and Stage Gates specify. Protected contents remain with authorized
custodians; discovery workers receive authorized receipts only.

Quarantine matching solution/answer lineage, current/future-target hints, private
evaluator contamination and unauthorized sources before release. Leakage is not
cured by deleting one exposed string; preserve the contaminated lineage and apply
the existing defect/version policy. A primary unseen cohort cannot contain targets
whose solutions or near-duplicate answer lineage occur in its history, even if the
episode predates T. Reject/quarantine the affected target lineage before outcomes;
do not delete otherwise eligible history examples to manufacture an unseen claim.
History eligibility is decided from the historical source contract, not by a
target-aware constructor retrofitting the dataset after reading future solutions.

## 4. Common training recipe design

**Proposed uniform method family: QLoRA**, using the same reviewed quantization,
compute-precision and LoRA workload policy for every eventual candidate. The design
reason is the free-compute constraint: explicitly control the frozen-base
representation rather than permit runtime-driven method switching. This is a
proposal, not proof of free-Colab feasibility. The companion
`DEVELOPMENT_SUBJECT_RECIPE_JUSTIFICATION_V1.md` now proposes 4-bit NF4, double
quantization and BF16 compute with explicit source-versus-design provenance.
Native baseline and adapted evaluations use the same reconstructed original-base
quantization/runtime profile so adapter effects are not confounded with a separate
baseline precision change. Source checkpoint identity and quantization lineage
remain pinned. The proposed common quantizer/precision policy is justified in the
companion memo; actual package/module/dtype mapping and capability remain later evidence.

Do not choose LoRA for one candidate and QLoRA for another based on fit, nor switch
at a later Colab session to make the selected subject fit. An insufficient runtime
is rejected. If a uniform justified QLoRA policy cannot be supported, undertake
explicit candidate-independent method review before comparison; no automatic
fallback is defined. Uniform plain LoRA would be a distinct workload version, not
an interchangeable resource comparison. No foundation training is authorized.

Proposed target rule: train low-rank residuals on every text decoder layer's
learned linear transformations forming attention queries, keys and values, and
mapping attention results back to the text residual stream. The independent
rationale is a bounded, interpretable attention-mediation intervention while
holding token embeddings, language-model head, feed-forward/expert/routing and
nonattention modality modules fixed; it does not claim optimal adaptation capacity.
This rule is not copied as a numerical Qwen30 recipe. No module name is hard-coded.
Fused transformations require a source-backed faithful partition; tied weights
require consistent accounting. Missing/nonlinear/custom transformations must be
reported against the rule; do not silently target fewer layers or substitute MLP
targets. If faithful mapping cannot be justified, mapping/comparability is blocked.

Parameter classifications retain source/role distinctions within the frozen design.
`FROZEN_VALUE` denotes inherited applicable controls without upgrading upstream status;
`DETERMINISTIC_RULE` denotes a fixed design policy. `PENDING_JUSTIFICATION` would be
a scientific-design blocker; none remains in this recipe.
`CANDIDATE_MAPPING_ONLY` and `RUNTIME_MEASUREMENT_ONLY` cannot choose the science.

| Parameter | Classification | Proposed rule/value or exact prerequisite |
| --- | --- | --- |
| Adapter method | DETERMINISTIC_RULE | Uniform QLoRA family for all candidates and native paired conditions; no capacity-driven LoRA/QLoRA switch. |
| Target-selection principle | DETERMINISTIC_RULE | All specified text attention input/output linear transformations, with the stated exclusions and no layer subsampling. |
| Exact architecture module mapping | CANDIDATE_MAPPING_ONLY | Prove each required mathematical transformation/module partition implements the rule; inventory/hash coverage. |
| Rank policy | DETERMINISTIC_RULE | Common rank 64 at every eligible attention transformation; reference-informed project choice, not all-linear effectiveness or candidate-specific tuning. See recipe memo. |
| Alpha/scaling policy | DETERMINISTIC_RULE | Alpha 16, standard alpha/r scaling; use_rslora=false. Reference-informed project choice with no superiority claim; see recipe memo. |
| Dropout | DETERMINISTIC_RULE | 0.0, preserving the existing disabled minimal-intervention rule. Intentional project departure from reference regularization, not an optimized value. |
| Loss | DETERMINISTIC_RULE | Teacher-forced accepted-completion supervision on section 2 loss-bearing shifted target tokens. Sum CE across the actual update group, ordinary or underfull, and divide by that group's actual loss-bearing target-token count; no per-example means, padding tokens, tail scaling to imitate 16, or double accumulation scaling. |
| Optimizer family | DETERMINISTIC_RULE | paged_adamw_32bit; explicit beta1=0.9, beta2=0.999, epsilon=1e-8, FP32 state; adopted documented ancillary choices, not silent defaults. See recipe memo. |

| Final incomplete effective batch | DETERMINISTIC_RULE | RECIPE_FINAL_BATCH_POLICY = FINAL-BATCH POLICY V1: for n complete eligible stage examples, q=floor(n/16), r=n mod 16; q ordinary updates, then exactly one final update on the remaining r real examples if r>0, otherwise none. Actual-token-normalized tail; total steps q+indicator(r>0). See contract below and recipe memo U02. |
| Native evaluation controls | FROZEN_VALUE | Inherit applicable draft3 controls/reserve/fairness exactly. Same pinned native quantization/runtime with adapter OFF baseline and ON adapted; no authoritative merge. Upstream proposed status is not upgraded. |

The single-pass coverage rule is derived from minimal **full** eligible-history
exposure: less than a complete visit violates the full-history intervention, and
extra visits introduce an additional dosage choice. It specifies a testable
minimal regimen, not a tuned optimum. The recipe justification memo supplies
proposed source/design choices for the previous numerical-policy gaps. The user
independently reviewed and authorized FINAL-BATCH POLICY V1 (memo U02): nominal
effective batch 16 has a predeclared smaller final optimizer batch when n is not
divisible by 16, preserving the more fundamental one-pass/full-history intervention.
Report that limitation; no numerical equivalence to a 16-example update is claimed.
**TRAINING_RECIPE_DESIGN is FROZEN_DESIGN**; no scientific recipe-design blocker remains.
This design freeze is not candidate-gate PASS or empirical feasibility.

For the tail's remaining r consecutive examples, sum cross-entropy over all actual
loss-bearing shifted target tokens under section 2's unchanged mask/terminal rules
and divide by their actual total count N_tail, which must be positive. Input,
template and padding tokens are excluded. Each microbatch contributes its summed
CE divided by that same N_tail; accumulate only within the tail, clip once after
the group, take exactly one optimizer step and one scheduler step. Preserve the
same optimizer, LR, scheduler, precision, adapter configuration and all other recipe
controls as ordinary updates. Ordinary groups use their own actual token denominator.

Every eligible example is visited exactly once; at most one underfull group exists
and it is last. Prohibit drop_last, dropping/repeating remainder examples, wrapping
to the beginning, gradient carry into a second pass, duplicating examples to reach
16, synthetic/filler examples, counting padding as examples, changing history
construction for divisibility, scaling tail loss to imitate 16, changing tail LR,
skipping its optimizer step, and candidate-specific tail behavior. If n=0, there
are zero updates and no adaptation claim; existing H0 semantics are unchanged.

Later training/resource manifests separately report n, q, r, ordinary update count,
whether a tail occurred, its actual example count and loss-bearing token count,
its microbatch/accumulation partition, and total optimizer steps q+indicator(r>0).
No-tail manifests report zero tail examples/tokens and a not-applicable tail partition.
Compared candidates/conditions use the same instantiated stage histories and n/q/r
schedule; tail size is a stage-history fact, not a candidate property. Only the
capacity-certified runtime partition may vary for capacity under the fixed objective.
No actual stage counts, token counts or runtime partitions are instantiated here.

No protected-population recipe search, per-candidate hyperparameter tuning based
on adaptation results, best-protected-score checkpoint, or desired-direction
parameter choice is permitted. If development-only tuning is later scientifically
required, its separate nonprotected population, selection rule and authorization
must be specified before use; it does not occur here and cannot silently replace
the common recipe. The smallest next task is described in section 8.

## 5. Deterministic local usability criteria

The machine class is inherited from the user's specification: Windows, 24 GB
system RAM, RTX 2050 with 4 GB VRAM. Actual usable resources/storage and conversion
location remain later evidence. No entire physical capacity is assigned to weights.
CPU serving/offload is permitted; paid/cloud AI inference is not.

A practical local route must load the derivative, authenticate identity/template,
and complete the fixed prototype envelope with the existing context/output
requirements, without OOM, driver/process/OS failure, safety-critical system
resource warnings, input clipping, unintended context rollover, lost output or
requirement of remote paid inference. Preserve host OS/application needs using
documented observed capacity and complete peak-resource accounting. No promise of
future free-memory availability or numeric spare-RAM threshold is made.

Before observations, define an authorized nonprotected fixed prototype-envelope
probe set from section 1's coverage rules, including complete replacement-output
framing. Every required probe must complete under the fixed controls. Report
load/prefill/response/save/conversion times and interruptions, usable/peak RAM,
VRAM/disk, offload/cache and runtime/OS identities. Success demonstrates local
operability, not target correctness or preservation of adapted behavior.
An interrupted/uncompleted probe remains unverified; it cannot be called feasible
because no explicit latency cap exists. G10/G11 source evidence/certification
still determine eligibility under the Stage Gates classification.

**Latency is a reported comparison dimension, not a numerical hard threshold.**
Record wall-clock observations with the same workload/assumptions; lower serving
burden follows Selection v1's evidence/dominance rules. No unplanned latency
threshold may later be used to reject a slow candidate or declare a faster one
materially superior. Failure to complete/resource failure is operational failure;
elapsed time alone has no accept/reject cutoff in this proposal. A later user-driven
