============================================================
PART 6 — LINEAGE / REDUNDANCY
============================================================

Do NOT define redundancy by vendor.

Construct lineage groups using:

1. base architecture lineage
2. checkpoint/training lineage where documented
3. tokenizer/serialization family
4. runtime/adaptation characteristics

Two models may be classified REDUNDANT REPRESENTATIVE only when they are
substantially the same experimental subject across those dimensions AND
retaining both would not materially test a different:

- architecture/adaptation regime
- serialization/protocol regime
- inference-resource regime
- adaptation-resource regime

Rules:

Same company != redundant.
Same license != redundant.
Same tokenizer alone != redundant.
Different parameter count alone != independent.

Explain every redundancy decision.


============================================================
PART 7 — FINAL DISPOSITIONS
============================================================

Use ONLY these dispositions:

FULL PREFLIGHT

TARGETED PREFLIGHT

INFERENCE-ONLY REFERENCE

REDUNDANT REPRESENTATIVE

EXCLUDE


Definitions:

FULL PREFLIGHT:
Model plausibly satisfies eligibility/I/A/P and represents a materially
useful experimental regime, but requires model-specific static verification
before infrastructure admission.

TARGETED PREFLIGHT:
One or a small number of unresolved facts could materially change its
classification. Investigate only those facts.

INFERENCE-ONLY REFERENCE:
Inference is plausible/relevant but repeated fresh-base adaptation is
clearly outside the currently evidenced practical regime or technically
unsupported. Do not treat it as a primary adaptation candidate.

REDUNDANT REPRESENTATIVE:
Covered by another retained representative under the frozen redundancy rule.

EXCLUDE:
Fails a required eligibility, current-protocol, or product-relevance gate,
or is clearly outside a meaningful self-hosted research regime.

Do not require a fixed number of survivors.


============================================================
PART 8 — RESOURCE-CONSTRAINED TIEBREAK
============================================================

Do NOT use this unless several NON-REDUNDANT FULL/TARGETED PREFLIGHT
candidates survive and available resources later require fewer preflights.

Apply this lexicographically, never as a weighted score:

1. EXPERIMENTAL COVERAGE GAIN

Prefer the candidate adding a regime not already represented across:

architecture/adaptation mechanism
→ serialization/protocol regime
→ adaptation-resource regime
→ inference-resource regime

2. ADAPTATION RELEVANCE

If tied, prefer stronger PRE-OUTCOME evidence that repeated fresh
ORIGINAL-BASE adaptation is technically testable.

Do not use evidence that it adapts better.

3. VERIFICATION BURDEN

If still tied, prefer fewer unresolved dependencies and a simpler
certifiable runtime/training stack.

4. RESOURCE BURDEN

If still tied, prefer lower expected infrastructure requirements based on
checkpoint/storage/topology/training-state facts available before inference.

5. STILL TIED

Retain both as unresolved candidates.

DO NOT invent a winner.

Benchmark scores, coding-quality judgments, project benchmark results and
adaptation outcomes are prohibited tiebreakers.
