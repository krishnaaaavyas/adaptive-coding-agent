# OrderFlow repository decisions

ID: OF-001
Decision: Organize the application into domain, application, persistence-interface, and in-memory-adapter modules.
Product reason: This keeps lifecycle behavior independent of storage while remaining understandable for a small application.
Status: ACCEPTED
Benchmark relevance considered: NO

ID: OF-002
Decision: Use UUID values generated by the application for customer, order, and shipment identifiers.
Product reason: Application-generated identifiers avoid coupling entity creation to a particular persistence implementation.
Status: ACCEPTED
Benchmark relevance considered: NO

ID: OF-003
Decision: Represent order and shipment states with string-valued enums.
Product reason: Enums make the finite lifecycle explicit and prevent arbitrary status values.
Status: ACCEPTED
Benchmark relevance considered: NO

ID: OF-004
Decision: Use synchronous in-memory repositories implementing small typing protocols.
Product reason: V1 requires process-lifetime persistence and storage replaceability without database or framework overhead.
Status: ACCEPTED
Benchmark relevance considered: NO

ID: OF-005
Decision: Treat product code as the identity of an order line and reject duplicate product codes within an order.
Product reason: OrderItem has no separate identifier, so unique product codes make item removal deterministic.
Status: ACCEPTED
Benchmark relevance considered: NO

ID: OF-006
Decision: Expose expected validation, missing-entity, and invalid-operation failures through a small application exception set.
Product reason: Callers need explicit failures without a framework-specific response layer or elaborate hierarchy.
Status: ACCEPTED
Benchmark relevance considered: NO

ID: OF-007
Decision: Do not add a CLI or HTTP interface in V1.
Product reason: The required deliverable is a local order-management component and no user interface is required.
Status: ACCEPTED
Benchmark relevance considered: NO

ID: OF-008
Decision: Add a database, ORM, dependency-injection framework, or messaging infrastructure.
Product reason: These dependencies do not serve V1's process-local storage and workflow requirements.
Status: REJECTED
Benchmark relevance considered: NO
